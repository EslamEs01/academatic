# Legacy ↔ Current Capability Ledger — MASTER (Spec 042)

**Method**: this ledger is a 1:1 transcription of the fifteen cluster audits
(`cluster-audits/C01-audit.md` … `C15-audit.md`). Each cluster section below carries EXACTLY the rows of that
audit's "Disposition summary (normalized — Spec 042 ledger source)" table — same capIds, same capability text,
same dispositions, same owners, byte-consistent. The additional attribute columns (legacy role/route, current
surface, reachability, modal/drawer status, states, privacy class, backend requirement, cross-role consumers,
visual status, required proof/test) are filled ONLY from each audit's own prose; where an audit genuinely does
not state an attribute the cell reads **not assessed (see audit)** — nothing is invented. `—` means
not-applicable by construction (e.g. a REJECTED_* capability has no current surface by law, or no future owner
because the refusal is final). Documentation only: nothing under `app/` was touched.

**Corpus totals (verified)**: **339 legacy pages** = 300 admin / 26 teacher / 13 family ·
**1,113 crawler screenshots on disk** (1,162 = the reference-imports mirror incl. 49 frontend-planning-deep
frames) · **1,723 raw records** = 679 HTML / 346 JSON / 359 MD / 339 TXT ·
**current 115 HTML / 57 bases / 50 nav items** (route split 24 deep / 25 plain / 1 lock ·
`FUTURE_ROUTES` `{}` · orphan set exactly `{gallery.html, gallery.en.html}`).
Per `exhaustive-evidence-inventory.md`: every one of the 339 legacy pages maps into at least one cluster
(union of memberships = 339 distinct pages, unassigned = 0); C15 carries 0 legacy pages by construction
(the crawler ran authenticated — auth/public UI was never captured).
